# Phase 23 Step 1 — Threat model (Security for external-network access)

> Written before any Phase 23 code — this is the "why" that Steps 2-6 (control channel HMAC, RTSP Digest auth, WebSocket signaling token, centralized logging, build/test/patch) are answering. Every claim below is backed by a specific line in the current source, not assumption — see the "Evidence" column.

## Why this document exists

Phase 24 (Remote/WAN access) puts the Pi's `8554/tcp` (RTSP), `40000/udp` (`ICE_AGENT_PORT`), `8765/tcp` (WebSocket signaling), and the sender's control-channel UDP port within reach of any device on the same Tailscale tailnet — not just devices on the physical LAN. Tailscale authenticates the *device* joining the tailnet; it says nothing about whether a given request arriving on those ports is a legitimate viewer versus another device (or, if the tailnet is ever shared, another person's device) doing something it shouldn't. Phase 23 exists to close that specific gap before Phase 24 ships. WebRTC media itself (SRTP/DTLS, Phase 22) is already covered and is out of scope here.

## 1.1 — Assets and attack surface

| # | Asset | Current exposure (evidence) | Why it matters once reachable outside the LAN |
|---|---|---|---|
| (a) | The video feed itself | Covered by SRTP/DTLS for the WebRTC path (Phase 22) already. RTSP/RTP path is still plaintext UDP (no SRTP) — flagged in the existing tech-debt section. | Anyone who can reach the RTP UDP stream on the wire can view/record it. Out of scope to fix RTSP encryption *in this phase* (that's a separate, larger change — RTSP's own `SETUP` negotiation would need an SRTP variant); Phase 23 instead focuses on **not letting an unauthorized party ever get to `PLAY`/`SETUP`** in the first place, which is the more immediate gap. |
| (b) | Control channel (bitrate/keyframe control) | `control_listener_thread_func()` (`src/network/control_listener_thread.cpp`) reads every UDP datagram on the control port and acts on it purely based on the first byte (`CONTROL_MSG_KEYFRAME_REQUEST` / `CONTROL_MSG_LOSS_REPORT`) — **no source-address check, no signature, no credential of any kind.** The 500ms `KEYFRAME_REQUEST_MIN_INTERVAL_US` rate limit exists only in `control_channel.cpp`, which is the *legitimate client's own self-throttling code* on the receiver side — it does **not** run on the listener that actually executes the request. A raw UDP packet sent directly to the listener's port bypasses it completely. | Once reachable from outside the LAN, anyone can force `bcm2835_encoder_force_keyframe()` on every packet (no rate limit enforced server-side) or force the adaptive-bitrate tier down to `BITRATE_LOW_BPS` — a low-effort but real DoS/quality-degradation vector against a single BCM2835 hardware encoder instance that every viewer shares. |
| (c) | RTSP session creation (`SETUP`/`PLAY`/`DESCRIBE`) | `handle_options()`/`handle_setup()` (`src/rtsp/rtsp_server.cpp`) dispatch on method with no `Authorization` header check anywhere in the file — confirmed by grep, zero matches for `Authorization`/`401`/`WWW-Authenticate`. | Anyone who can reach `8554/tcp` can `SETUP`+`PLAY` a session today — this is currently bounded by "must be on the LAN," which Phase 24 removes. The 5-session hard limit (Phase 20) caps *how many* unauthorized sessions, not *whether* they're authorized. |
| (d) | WebRTC session creation (WebSocket signaling) | `do_websocket_handshake()` (`src/signaling/signaling_server.cpp`) completes the RFC 6455 handshake and returns `101 Switching Protocols` for any client that sends a well-formed WebSocket upgrade request — no path, query, or header check gating it. | This is the highest-cost entry point per request on a 1GB-RAM Pi: a completed handshake leads into offer/answer parsing, DTLS certificate/keying work, and (per Phase 22.6) a dedicated per-session handshake thread over a memory-BIO. Unauthenticated + reachable from any tailnet device means anyone can spin up an arbitrary number of these — a more effective DoS lever than (b) or (c), and the one most worth gating **before** any other work happens for that connection. |
| (e) | Admin dashboard login/session (Phase 25) | `admin_http_server.cpp` on port 80: `ADMIN_USERNAME`/`ADMIN_PASSWORD` env vars (fail-closed at startup, same pattern as (c)/(d)), `CRYPTO_memcmp`-compared, gate an in-memory random session (`admin_session.cpp`, `RAND_bytes(32)` id, `HttpOnly; SameSite=Strict` cookie). Rate-limited via the same `auth_failure_log.h` (c)/(d) already use. **Plain HTTP, no TLS** — this port has no WSS-equivalent (24.6 only covers the WebSocket signaling port). | The login form's username/password, and the session cookie itself, both travel in cleartext on the wire. Same accepted-risk shape as (a)-(d)'s "only reach this over Tailscale/LAN" reasoning in 1.2 below — the residual risk here is real (unlike RTSP Digest, this scheme *does* put the password itself on the wire) and this port must never be port-forwarded to the public internet without adding TLS first. |
| (f) | The two admin-only WebSocket message types (`force-keyframe`, `get-viewers`) | `main.cpp`'s `on_signaling_message()`: both require a `admin_session` field valid per (e)'s session store, checked in addition to (d)'s `SIGNALING_TOKEN` gate the WebSocket connection itself already passed. | `SIGNALING_TOKEN` alone only ever proved "may open a recvonly WebRTC viewing session" (anyone using `webrtc_test.html` has it, by design — it's meant to be shareable with ordinary viewers). Without this second check, anyone who knows that token could force keyframes stream-wide (denying other viewers a clean picture on demand) or read every viewer's connection stats (ufrag, duration, loss/jitter) — capabilities the admin login is supposed to be gating, not incidental side effects of viewing. |

## 1.2 — Confirms: Tailscale does not substitute for any of the above

Tailscale (Phase 24) authenticates which *device* is allowed onto the tailnet and can restrict, via ACLs, which devices may reach which of the Pi's ports. It has no visibility into, and makes no claim about, what a device does with a connection once its ACL allows it through — that's the application's job. Concretely: an ACL can say "only my phone and my laptop may reach port 8765," but it cannot distinguish "my phone's legitimate viewer page" from "any other process running on my phone" opening a raw WebSocket to that same port. Sub-phases 23.2-23.4 are that missing layer. This also means Phase 23's authentication is deliberately scoped as **defense-in-depth against other processes/devices already inside the tailnet**, not a replacement for Tailscale's own device-level ACLs (23.1 already covers configuring those — no code, pure network config, done as Phase 24 Step 24.1).

## 1.3 — Decision: mechanism chosen per asset

These decisions are what Steps 2-4 (23.2-23.4) implement; recorded here so the "why" isn't re-litigated mid-implementation.

| Asset | Chosen mechanism | Why this one | Alternatives considered and rejected |
|---|---|---|---|
| (b) Control channel | HMAC-SHA256 (OpenSSL) appended to every control datagram, keyed by a shared secret configured at `camera_app` startup | Datagrams are tiny and fixed-format already (`control_protocol.h`) — a MAC is the minimal addition that lets the listener cryptographically reject forged datagrams without changing the wire format's shape, and reuses OpenSSL, already a project dependency since Phase 22 (no new external dependency). Symmetric because both ends (sender's `camera_app`, receiver's `camera_receiver`) are code the project itself controls and deploys together — no need for asymmetric crypto here. | A per-source-IP allowlist was considered instead of/alongside a MAC, but on a Tailscale tailnet with potentially more than one authorized device, an IP allowlist would need updating every time a device's Tailscale IP changes and gives no protection against another *authorized* tailnet device misbehaving — a MAC keyed by a secret only the legitimate receiver knows is strictly stronger for the same effort. |
| (c) RTSP | Digest Authentication per RFC 2326 §17 (RFC 2617 challenge/response) | RTSP already has a standard auth mechanism every RTSP client (VLC, ffplay, browsers via `rtsp://user:pass@host`) understands out of the box — no custom client-side work needed, unlike a bespoke scheme. Digest specifically (not Basic) because it never puts the password on the wire even in the clear, which matters as defense-in-depth per 1.2 above even though Tailscale already encrypts the transport. | Basic Auth was considered and rejected for the reason above. A custom pre-shared-token-in-URL scheme (mirroring 23.4's WebSocket approach) was also considered, but RTSP's own Digest mechanism gets the same effective protection "for free" via existing client support, so there is no reason to hand-roll a substitute here specifically. |
| (d) WebSocket signaling | Pre-shared token as a query parameter, checked before completing the WebSocket handshake | The check has to happen at (or before) `do_websocket_handshake()` — before any DTLS/offer-answer work starts — to actually address the DoS concern in row (d) of 1.1. A query-parameter token is the simplest thing that works from an unmodified browser `WebSocket()` constructor (no custom-header support needed), and keeps the change localized to `signaling_server.cpp` plus the viewer HTML page. | HTTP Basic Auth on the initial handshake request was considered (WebSocket handshakes are technically regular HTTP requests before the 101 upgrade) — rejected only because a query-parameter token is marginally simpler to wire into a plain browser page than adding an `Authorization` header to the handshake request, and the security property is equivalent given both ride over the already-encrypted Tailscale tunnel. |
| (e) Admin login | Username/password (env vars, `CRYPTO_memcmp`), server-generated random session id in an `HttpOnly` cookie | Same plaintext-credential-in-env-var precedent as (c)/(d) (no new pattern introduced) - a session cookie (not re-sending the password on every request) is standard practice once a login form exists, and `HttpOnly` keeps the cookie itself out of reach of any JS running on the page (defense against XSS, even though this project doesn't currently have a known XSS vector). | A JWT/stateless-token scheme was considered and rejected: this project has exactly one admin identity and a handful of concurrent sessions at most, so the added complexity (signing key management, expiry-in-token vs. revocation) buys nothing a simple in-memory map (same shape as every other registry in this codebase) doesn't already provide, and a stateless token can't be revoked on logout the way this store's `admin_session_destroy()` can. |
| (f) Admin-only WS commands | A second field (`admin_session`) on top of the already-token-gated WebSocket, validated against (e)'s session store | Cheapest correct fix once (e) exists - reuses the same store, one field check per privileged message type, no new transport/connection needed. | Standing up a second WebSocket connection (or a separate authenticated HTTP API) for just these two commands was considered and rejected as needless complexity - the existing signaling WebSocket is already open, already per-session, and `main.cpp`'s dispatch is already a flat if/else-chain these two branches drop into naturally. |

## What Step 1 deliberately does not decide yet

- Exact config/secret-provisioning mechanism (file vs. env var vs. both) for the two independent secrets (control-channel HMAC key, signaling token) — left to Steps 2 and 4 respectively, since it's an implementation detail that doesn't change the mechanism choice above.
- The RTSP username/password pair's provisioning — same reasoning, deferred to Step 3.
- Whether to add IP-based temporary blocking on repeated auth failures (23.5) — noted as a "consider" in the roadmap breakdown, decided once real failure-log volume from 23.2-23.4 gives a sense of whether it's warranted.
