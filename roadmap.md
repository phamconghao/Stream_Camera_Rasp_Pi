## Phase 23 (Security for external-network access) breakdown

> Reordered ahead of Phase 24 (Remote/WAN access) on purpose: the plan is to reach external devices over a VPN (Tailscale — see Phase 24), but VPN membership only authenticates the *device*, not the *application-layer request*. Three data paths are currently plaintext/unauthenticated and must not be reachable from outside the LAN until this phase lands: the control channel (`control_channel.cpp`/`control_listener_thread.cpp`), the RTSP server (`rtsp_server.cpp`), and the WebSocket signaling server (`signaling_server.cpp`). WebRTC media itself is already covered (SRTP/DTLS, Phase 22) and is out of scope here.

| Sub-phase | Content | Status | Notes |
|---|---|---|---|
| 23.1 | Threat model | ⏳ Not started | Confirm the assets to protect once reachable outside the LAN: (a) the video feed itself, (b) the control channel (unauthenticated bitrate/keyframe-request abuse), (c) RTSP SETUP/PLAY (unauthenticated session creation), (d) WebSocket signaling (unauthenticated WebRTC session creation — notable DoS surface on 1GB RAM, since each accepted offer spins up a full DTLS handshake thread). Confirms which of Step 2-4 below actually matter and in what order. |
| 23.2 | Control channel authentication (HMAC-SHA256) | ✅ Done | Trailing 32-byte HMAC-SHA256 (`common/hmac.{h,cpp}`, OpenSSL, constant-time verify via `CRYPTO_memcmp`) appended to both `CONTROL_MSG_KEYFRAME_REQUEST` and `CONTROL_MSG_LOSS_REPORT` datagrams — see `control_protocol.h`'s `CONTROL_MSG_HMAC_SIZE`. `control_channel.cpp` (receiver-executable side) signs; `control_listener_thread.cpp` (sender-executable side) verifies before acting, drops + rate-limited-logs on mismatch (`log_auth_failure()`, 5s summary window, separate from `KEYFRAME_REQUEST_MIN_INTERVAL_US`). RTCP RR relayed via `control_channel_send_raw()` intentionally left unsigned — it's log-only, never actioned (see that function's comment). Shared secret is a required `CAMERA_CONTROL_SECRET` env var on both `camera_app`/`camera_receiver` — **fail-closed**: both refuse to start (verified: exit 255) if it's missing/empty, rather than falling back to an unauthenticated or default-keyed mode. Build: clean `-Wall -Wextra -Wpedantic -Werror` for both executables (verified by installing `libcamera-dev`/`libssl-dev`/`libsrtp2-dev` and running a real `cmake --build`, matching the CI workflow's exact package list — confirmed no CI workflow change needed). Tested: 6/6 standalone HMAC unit tests (valid verify, every single tampered MAC byte, tampered payload, wrong secret, wrong-length MAC, real 5-byte loss-report-shaped payload) + a real UDP end-to-end test against a harness using the actual `hmac.cpp`/dispatch logic — valid messages ACCEPT, wrong-secret and tampered-byte forgeries REJECT, and a pre-Phase-23-format forged packet (1 byte, no HMAC) is correctly UNRECOGNIZED rather than treated as a valid request, closing the exact gap flagged in `docs-security-threat-model.md` row (b). |
| 23.3 | RTSP Digest Authentication (RFC 2326 §17 / RFC 2617) | ✅ Done | Classic RFC 2069/2617 no-`qop` Digest (`MD5(HA1:nonce:HA2)`) implemented in `rtsp_server.cpp` — `401 Unauthorized` + `WWW-Authenticate: Digest realm="rpi-camera", nonce=..., algorithm=MD5` on missing/invalid `Authorization`. **Scope widened from the original plan**: applied to `SETUP`/`PLAY`/`DESCRIBE`/`TEARDOWN` (not just the first three) after finding `rtsp_session_registry.cpp`'s session IDs are an 8-hex-digit **monotonic counter**, not a random token — so the originally-planned "authenticate once at SETUP, trust the Session header after that" scheme was dropped in favor of verifying Digest credentials on every non-OPTIONS request. Nonce is generated once per TCP connection (`RAND_bytes`, 16 bytes/32 hex chars) and reused for that connection's lifetime — bound to the connection itself (not tracked server-side with expiry), so a response computed against one connection's nonce is meaningless replayed on another. Comparison of the response hash uses `CRYPTO_memcmp` (constant-time). Credentials are required `RTSP_USERNAME`/`RTSP_PASSWORD` env vars, checked fail-closed in `main.cpp` before any hardware/thread init (verified: exit 255 if either is missing, confirmed to run *before* camera hardware is touched). Build: clean `-Wall -Wextra -Wpedantic -Werror` (full `cmake --build`, same as Step 2). Tested: 11/11 end-to-end cases against an isolated test harness compiled from `rtsp_server.cpp`'s real object code (stubbing only `pipeline_controller`/`sps_pps_cache`/`udp_sender` to avoid needing camera hardware) — OPTIONS bypasses auth, DESCRIBE/SETUP/TEARDOWN all correctly 401 without credentials, wrong password rejected, correct credentials accepted, and critically: a nonce from one TCP connection replayed with correct credentials on a *different* connection is rejected, proving the connection-bound nonce design actually holds. |

## Phase 24 (Remote/WAN access) breakdown

> **Direction finalized 2026-08-30, after a real failed test:** a genuine no-Tailscale attempt (iPhone on cellular data, Tailscale off, real public IP + a temporary Cloudflare tunnel for signaling only) failed at the ICE connectivity-check step - the Pi's router never had UPnP available either (`upnpc -l` → "No IGD UPnP Device found", confirmed on this Pi), and the user cannot access the router's admin UI to add a manual port-forward (24.5). Rather than requiring a paid third-party `coturn` VPS (24.4's code-complete but server-less TURN path) just to reach mobile/cellular viewers, **the user chose to make Tailscale the official transport for both RTSP and WebRTC** - reverting the "browser viewers need nothing installed" pivot from below. Practical effect: 24.1/24.2 are exactly as valuable as originally planned again; 24.3 (STUN)/24.4 (TURN)/24.6 (WSS) remain in the codebase as real, tested, working infrastructure - genuinely useful if a real public deployment (with a real domain + `coturn` VPS) happens later - but are no longer on the critical path for "watch the camera remotely" *today*; 24.5 (router port-forward) and 24.7 (verify WebRTC without Tailscale) are deprioritized, not abandoned - either could resurface if the no-VPN goal comes back. 24.8 (verify RTSP over Tailscale) is now the one directly relevant remaining checklist item, since WebRTC-over-Tailscale is already confirmed (real iPhone, Safari, 2026-08-30).
>
> Original pivot reasoning kept below for context on *why* 24.2-24.6 exist and work the way they do - none of that engineering was wasted, it's just not required for the currently-chosen path.
>
> Current state before this phase: `signaling/ice_candidate.h` only ever generates a **host candidate** (the Pi's own LAN IP). Its docstring said so explicitly: *"this project targets LAN/simple-NAT use where a host candidate is normally sufficient"*. `signaling/ice_agent.h` also only implements the responder half of ICE. In practice this means a phone or laptop on a different network (different Wi-Fi, or cellular 4G/5G) currently **cannot** view the camera over either WebRTC or RTSP.
>
> **Direction changed mid-Phase-24 (after 24.1/24.2 were planned/started as Tailscale-only):** the original plan required every viewer device — not just the Pi — to install Tailscale. New requirement: **browser/WebRTC viewers must not need to install anything.** RTSP (VLC/ffplay) is explicitly kept Tailscale/LAN-only — RTSP has no NAT-traversal mechanism of its own and no encryption (see Phase 23's accepted limitation below), so it stays behind the VPN rather than exposed publicly.
>
> This means WebRTC now needs real NAT traversal instead of relying on Tailscale's tunnel: a **STUN client** (24.3, gathers the Pi's server-reflexive/public IP:port — `ice_agent.h` currently only answers STUN, never initiates it) and a **TURN client** (24.4, relays media through a third-party relay server for NATs where a direct/reflexive path still doesn't work — e.g. symmetric NAT, common on cellular carriers). TURN needs an actual TURN server; this project will run **coturn** (the standard, widely-audited open-source STUN/TURN server) on a small VPS rather than hand-rolling RFC 5766/8656's allocate/permission/channel-bind exchange from scratch — treated the same way this project already treats OpenSSL/libsrtp2: infrastructure-critical protocol code where an audited implementation is the responsible choice, not a media-pipeline component this project's from-scratch philosophy is actually about. **Flagging this explicitly since it's a new third-party server dependency, not just a client-side library — revisit if that trade-off doesn't sit right.**
>
> Opening WebRTC to the public internet also invalidates Phase 23's accepted limitation (*"no TLS for RTSP/WebSocket... because these paths are expected to only be reached over the Tailscale VPN tunnel"*) for the **signaling** path specifically: `signaling_server.cpp`'s `?token=...` auth is a static bearer credential sent in cleartext over WebSocket, and without a VPN tunnel encrypting the whole connection, a network observer between the browser and the Pi could read and replay it. RTSP's Digest auth doesn't have this specific problem (it never sends the password itself, only a nonce-bound hash) and stays on Tailscale anyway per the direction above, so it's unaffected. Fix: **24.6 wraps the WebSocket signaling server in real TLS (WSS)** using a Let's Encrypt certificate — self-signed is not an option here since browsers refuse/warn on it, unlike the DTLS media path's self-signed cert (`dtls_cert.cpp`), which browsers accept because WebRTC verifies it via the SDP fingerprint, not a CA chain.

## Phase 25 (Admin dashboard) breakdown

> Motivation: the only way to watch the camera in a browser was `webrtc_test.html` - a debug page with a step-by-step handshake checklist, requiring the raw `SIGNALING_TOKEN` pasted into a URL field by hand. The user wanted a real "type the Pi's IP, log in, watch" flow instead, with operational controls (force a keyframe) and live per-viewer stats (who's watching, for how long, at what loss/jitter). `webrtc_test.html` and its `?token=` auth are untouched - this is a new, parallel path.

## Giới hạn/nợ kỹ thuật đã biết (chưa chặn chức năng, nhưng đáng lưu ý)

- `bcm2835_encoder_encode_frame()`/`bcm2835_decoder_decode_frame()` luôn dùng buffer OUTPUT index cố định thay vì luân phiên — an toàn vì gọi đồng bộ (QBUF ngay sau DQBUF), nhưng chặn khả năng pipeline hóa song song nhiều frame.
- `control_channel`/`control_listener_thread` không có xác thực — bất kỳ ai gửi đúng gói UDP tới đúng port đều có thể ép sender đổi bitrate/tạo keyframe liên tục (không phải lỗ hổng nghiêm trọng ở quy mô LAN cá nhân, nhưng cần khắc phục trước khi expose ra Internet).
- Admin dashboard's HTTP server (`admin_http_server.cpp`, port 80) is plaintext - no TLS. Same accepted-risk shape as RTSP/legacy-signaling's own plaintext (see `docs-security-threat-model.md`'s (e)/(f) rows) - safe only because this project's supported access path is Tailscale/LAN, never a direct port-forward to the public internet.
- Dashboard (`dashboard.html`) yêu cầu chạy HTTP server riêng ở đúng thư mục chứa `sender_stats.json`/`receiver_stats.json` — chưa có cách xem gộp cả 2 phía trên cùng 1 trang do sender/receiver thường là 2 máy khác nhau.
- `frame_pool.cpp`/`frame_queue.cpp` (thiết kế pool/queue generic cũ) vẫn còn trong `CMakeLists.txt` dù không được gọi ở đâu — an toàn để xóa khi thuận tiện.
- `rtsp/rtsp_server.cpp`'s `PLACEHOLDER_SERVER_RTP_PORT`/`PLACEHOLDER_SERVER_RTCP_PORT` (SETUP response's `Transport` header) là giá trị advertise cố định, KHÔNG phản ánh cổng nguồn UDP thật (từ Phase 20 bước 4, `udp_sender.cpp` dùng 1 socket dùng chung, cổng do OS tự cấp) — vô hại với hầu hết client (chỉ dùng để hiển thị/đoán cổng RTCP), nhưng nếu có client thực sự dựa vào giá trị này thì cần plumbing cổng thật ra từ `udp_sender.cpp`.
